# 2. Feature & flow layer: a catalogue of intentions read off the C4 model

Date: 2026-11-05

## Status

Accepted.

## Context

The map answers *what this system is made of*. It cannot answer *what this system lets you do*, which
is the first question a newcomer actually has. A feature catalogue — named intentions, grouped into
categories, each naming the model elements it touches — answers it.

Naming intentions is a judgment call, and a catalogue is only worth reading if it stays true as the
code moves. Those two facts pull in opposite directions, and the decisions below are where that
tension was resolved. None of them is obvious from the code.

## Decisions

### No code in this layer calls a model API

Naming a feature needs a model. Every line this layer adds is nonetheless deterministic: entry-point
discovery, catalogue validation, the append-only merge, the broken check. The non-deterministic step
is performed by the user's own agent, outside this codebase — `seeforce annotate` already prints
instructions and lets the agent write, and catalogue generation follows that pattern through MCP.

This is the only arrangement under which Principle III of the constitution holds for everything
inside the repo. It also keeps the layer free of an API key, a budget and a vendor.

Rejected: calling a model from the CLI. It makes the output unreproducible, puts a paid dependency on
the critical path of a scan, and moves the constitution's boundary inside the code instead of outside it.

### The catalogue is its own artifact at `.seeforce/features.json`, never inside `workspace.json`

`workspace.json` is a pure scan artifact, regenerated byte-identically from the annotations. The
catalogue is reviewed content with a human marker on it, so it cannot live in a file that a scan
overwrites. JSON, not YAML: nobody edits it by hand — an agent writes it and an agent corrects it.

The catalogue is therefore explicitly excluded from the byte-identical gate, and travels to the app
with the model in the same import rather than through a second channel.

### Feature identity is the snapshot path `"Component (Container)"`, and a collision fails the load

The catalogue names model elements, and the delta comparison already keys elements by that path
string. Reusing it keeps the catalogue a *reading* of the model, asserting no structure of its own,
and needs no new identifier format.

The cost: derived identity collides when two model elements resolve to one path. The layer refuses to
load rather than resolve the ambiguity silently, on the same reasoning as ADR 0001 — a partial
catalogue that looks complete is worse than a loud failure.

### A review is attested by the commit; generation never advances the marker

`reviewed_at` holds a git commit SHA, or null for generated-but-unreviewed. Generation MUST NOT set
it. Making the commit the attestation means the only way a feature becomes reviewed is a human act
that leaves a trace, and an agent regenerating the catalogue cannot promote its own output.

The merge is append-only for this reason: a reviewed feature stays byte-identical across
regenerations. New features are detected through entry points, not by re-running discovery and
diffing — discovery over one commit was measured at 18 features versus 14 across two runs, so a
re-run is not a reliable signal of change.

### A path starts at the component that receives the request, not at a person

Human actors are out of v1. The receiving component is the first element the model actually declares,
so a path that starts there needs no element the map does not already have.

### Drift is signalled by `seeforce delta` and nowhere else

The broken check — a feature whose named elements intersect the elements a delta removed — extends
`seeforce delta`, reusing its existing pairing rather than adding a second comparison path. It exits
non-zero and writes nothing.

A broken feature is validated against the **base** snapshot, not the head one. A feature is broken
precisely because it names an element the head model no longer declares, and an unresolvable element
is otherwise a fatal load error — so validating the catalogue against head would report every broken
feature as a failed load and make the exit code that fails CI unreachable. The base is also the
snapshot the catalogue was reviewed against. A feature naming an element that exists in neither
snapshot is a stale catalogue and still fails to load.

No drift verdict is stored or displayed. A divergence breaks CI, and that is the whole mechanism: a
stored verdict would need its own freshness story, and a stale "broken" badge in the UI is a worse
artifact than a red pipeline. The feature list and the restricted per-feature view *are* in v1; only
drift indicators are excluded.

## Consequences

Three components carry the layer, all inside *Annotation Parser*: **Feature Catalogue** (load,
validate, merge), **Entry Point Discovery** (the deterministic extractors), and the existing **Delta
Reporter**, extended with the broken check.

Slice 1 ships as four changes — parser, then CLI and CI, backend and frontend — with the backend and
frontend able to proceed in parallel once the parser lands. The value line is at the CLI, not at the
frontend: a catalogue that breaks CI when it goes stale is useful before anything renders it.
